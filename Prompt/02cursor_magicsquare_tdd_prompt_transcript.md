# 설계 문서 필수 목차 (이 순서·제목 유지)

## 0. Executive Summary
- 한 줄 목표, 1차 범위(판정) vs 2차 범위(생성), 이번 문서가 해결하는 것 / 하지 않는 것

## 1. 전제 및 문제 정의 정렬
- 문제 정의 보고서와의 **추적 표** (I-1~I-10, T-1~T-7 → 본 설계에서 어떻게 다루는지)
- 표면 정의 vs 정확한 정의 — **본 TDD 설계가 따르는 쪽** 명시

## 2. In Scope / Out of Scope (TDD 설계 단계)
- **In:** 4×4 유효성 판정, 계약, 테스트 레이어, 시나리오, 실패 유형, 회귀 원칙
- **Out:** 구현 언어, 생성 알고리즘, UI, n×n, 모든 해 나열 등 (근거 한 줄씩)

## 3. 1차 계약 결정 (열린 질문 해소)

문제 정의 보고서 STEP 4·5의 열린 질문을 **설계 결정**으로 고정하고, **대안·선택 이유·Trade-off**를 표로 남기십시오.

반드시 결정할 항목:

| ID | 결정 주제 | 요구 |
|----|-----------|------|
| **D-1** | 1차 계약 범위 | **유효성 판정만** 1차 vs 판정+「한 해 생성」포함 — **1차는 판정만**으로 고정할지, 포함 시 2차로 미룰지 **명시** |
| **D-2** | 판정 결과 형태 | `bool`만 vs **위반 종류·위치(행/열/대각/집합/형태)** 반환 — **권장안 + 이유** |
| **D-3** | 입력 표현 | 4×4 2D 배열 vs 1차원 16개 vs 경계 케이스(빈 값·null·길이 불일치) — **허용 입력·거부 입력** |
| **D-4** | 검사 순서·단락 | I-1 실패 시 I-4~I-7 검사 여부 등 **단락(short-circuit) 정책** |
| **D-5** | 마법 상수 | M=34 **고정** vs 파라미터 — 4×4 범위에서의 결정 |

각 결정은 **「테스트로 고정할 계약 문장」** 1문장으로도 적으십시오.

## 4. 도메인 모델 (구현 무관, 개념만)

- 핵심 개념: 격자(Grid), 칸(Cell), 선(Line: 행/열/대각), 판정 결과(ValidationResult) 등 — **역할만**, 코드 없음
- **검증 책임** vs **생성 책임** 분리 다이어그램 (mermaid 또는 ascii)
- I-1~I-10을 **검사 단위·의존 관계**로 매핑한 표

## 5. 불변식 → 테스트 관심사 매핑

| Invariant | 검사 내용 | 대표 무효 패턴 | 테스트 레벨 제안 (단위/통합/계약) |
|-----------|-----------|----------------|-----------------------------------|
| I-1 ~ I-10 | (채울 것) | (채울 것) | (채울 것) |

- **I-8**(전부 만족 시에만 유효), **I-9**(결정론), **I-10**(규칙 변경=계약 변경)용 **회귀·스냅샷 원칙** 별도 절

## 6. 테스트 전략 (TDD)

- **Red → Green → Refactor**를 이 프로젝트에 적용할 때의 의미 (판정 절차 관점)
- 테스트 **피라미드** 또는 **레이어** (예: 순수 규칙 / 조합 판정 / 경계·오류)
- **테스트 이름 규칙** (Given-When-Then 또는 `should_..._when_...` 등 — 하나로 통일)
- **픽스처·골든 격자** 원칙: 알려진 유효 1개 이상, 무효 유형별 최소 1개
- **대리 지표 거부(T-6):** 「격자 한 장 통과」≠ 완료 — 문서에 명시

## 7. 최소 판정 시나리오 목록 (핵심 산출물)

아래 **유형별로 최소 1개 이상** 시나리오를 표로 작성하십시오.  
각 행: `시나리오 ID`, `설명`, `입력 요약`, `기대 판정`, `주요 위반 Invariant`, `우선순위(P0/P1)`, `비고`

**필수 유형 (누락 금지):**

1. 알려진 **완전 유효** 4×4 격자 (골든)
2. **행 합만** 어긋남 (다른 제약은 만족에 가깝게)
3. **열 합만** 어긋남
4. **주대각** / **부대각** 각각 어긋남 (2행 이상)
5. **중복** (I-3)
6. **범위 밖** 값 (I-2)
7. **크기·형태** 위반 (I-1: 3×4, 4×3, 16칸 아님 등)
8. **합은 맞지만 순열 아님** (I-4~7 만족·I-3 위반 — 문제 정의의 주의 사례)
9. **동일 입력 재판정** (I-9)
10. **경계 입력** (D-3에서 거부로 정한 것)

시나리오 표 아래에 **「P0만으로 1차 TDD 착수 가능한지」** Yes/No와 근거 3문장.

## 8. 테스트 케이스 초안 (구현 전 명세)

- §7 시나리오 중 **P0**를 테스트 케이스 ID(`TC-001`…)로 변환
- 각 TC: 전제(Given), 실행(When), 기대(Then), **실패 시 관찰 가능한 정보** (D-2와 정합)
- **코드·assert 문·프레임워크 API 없음** — 자연어 또는 표만

## 9. 2차 목표(선택): 유효 격자 하나 산출

- 1차 판정 TDD **이후**에만 다룰 **별도 계약·별도 테스트 스위트** 개요 (1페이지 이내)
- 1차와 **섞이면 안 되는 이유** (책임 혼동 방지)

## 10. 리스크·가정·미결정

- 가정 목록 (예: 정수만, 음수 없음)
- 미결정은 **「구현 착수 전 사용자 확인 필요」**로만 남기고, 임의로 언어·도구를 정하지 말 것

## 11. 다음 단계 (구현 착수 체크리스트)

- 구현 전 확인할 체크박스 5~10개 (예: P0 TC 동의, D-1~D-5 확정, 골든 격자 합의)
